# M2 Security Kernel — Defensive Threat Model

> Status: `PROPOSED / NOT IMPLEMENTATION`.  
> Final pack status: `M2 SPECIFICATION — PROPOSED`.  
> All content is defensive and focused on protecting AERON. No exploit instructions are provided.

## 1. Scope

This threat model covers the proposed M2 Security Kernel components: OwnerAuthorityGuard, PolicyDecisionEngine, OwnerApprovalService, parameter-hashing infrastructure, AuditLedger, and Windows Security Vault. It assumes AERON remains a native Windows .NET 10 LTS/WPF desktop application, remote-only inference, ₹0 budget, OmniRoute untouched, no local model weights/runtimes, no paid API fallback, no skill scripts, and ultimate Owner authority.

## 2. Threat matrix

| Threat | Attack surface | Security objective | Prevention | Detection | Recovery | Required automated tests |
|---|---|---|---|---|---|---|
| Malicious or compromised agents | Agent-to-agent messages, task requests, delegated calls, prompt/tool payloads | Prevent any agent from bypassing Owner authority or policy | Bounded authorization inheritance; OwnerAuthorityGuard as non-bypassable choke point; default deny; no third-party agent framework; agent output never treated as policy | AuditLedger records actor, agent chain, policy version, decision, and denial reason; redaction applied | Owner preemption invalidates pending approvals and denies new consequential actions; quarantine proposed for future implementation | Agent inheritance tests; conflicting-instruction precedence tests; Owner preemption tests; no-direct-guard-bypass architecture tests |
| Prompt injection | Remote model output, local documents, user-provided text, memory/context, tool results | Prevent untrusted text from becoming authority or policy | Treat all text as untrusted data; deterministic PolicyDecisionEngine separate from model/agent reasoning; explicit action classification; deny ambiguous requests | Policy-evaluation evidence and redacted logs record attempted classification and denial | Deny action; preserve audit record; require fresh explicit Owner request/approval | Prompt-injection-as-data tests; no-policy-elevation tests; ambiguous-request rejection tests; redaction tests |
| Unauthorized tool execution | Future compiled tool registry, scheduled actions, external process launch, local file writes | Ensure no consequential side effect without policy decision and approval | Default-deny; `L2`/`G3`/`G4` approval gates; parameter hash; revalidation immediately before execution; no skill scripts | AuditLedger records request, decision, approval hash, and outcome | Deny on missing/expired/cancelled/mismatched approval; Owner preemption cancels pending work | Tool-execution gate tests; approval-before-side-effect tests; mismatch tests; skill-script ban tests |
| Privilege escalation | Policy files, configuration, role/delegation claims, Owner-state manipulation | Preserve Owner supremacy and least privilege | Owner authority non-delegable; policy versioning; current-user Windows ACLs; no inline credentials; `L3` hard-denied actions; fail closed on missing policy state | Startup audit verification; config-policy tests; audit chain verification; redacted denial logs | Deny on policy-version mismatch or unknown role; restore last verified policy version after Owner review | Privilege-escalation unit tests; policy-version mismatch tests; config invariant tests; ACL/path tests |
| Approval replay | Reused approval IDs, captured approval tokens, duplicate execution, delayed scheduled execution | One approval may authorize only one exact action | Unique approval ID, nonce, expiry, exact parameter hash, single-use state, revalidation immediately before execution | AuditLedger detects duplicate approval ID/hash reuse; redacted replay-denial record | Deny replay; require new explicit Owner approval | Replay tests; duplicate-ID tests; expired-approval tests; single-use state tests |
| Parameter tampering | Action payloads, destination fields, data classification, scheduling parameters, serialized requests | Bind approval to exact intended parameters | Protected exact-operation binding distinct from redacted display/audit; recompute before side effect; fail closed on mismatch; material differences must not collapse through redaction | Parameter-mismatch audit events; policy-evaluation evidence mismatch | Deny execution; preserve original and recomputed hashes in redacted audit record | Hash determinism tests; field-order tests; Unicode/number/date canonicalization tests; mismatch fail-closed tests |
| Secret leakage | `aeron.config.json`, logs, prompts, memory, approval UI, audit records, backups, exceptions | Zero secret exposure in configs, logs, prompts, memory, or backups | `RedactionFilter`/`RedactingLogger` reuse; `ConfigPolicyValidator`; DPAPI/Credential Manager vault; zero secrets in `aeron.config.json`; Windows ACLs; no raw secret in audit or persisted binding material; protect any secret-dependent binding against guessing | Redaction tests; config rejection tests; audit/log secret scans; backup content checks | Deny secret-bearing action; rotate/delete secret through Owner-approved vault lifecycle; redact retained records | Existing redaction tests extended; nested-exception tests; structured-property tests; vault round-trip tests; zero-secret config tests |
| Audit-log tampering | SQLite WAL files, audit table, backup copies, startup verification | Tamper-evident, append-only, recoverable audit trail | Hash chain with previous/current hashes; append-only persistence; separately protected checkpoint or equivalent for whole-chain replacement/truncation; SQLite WAL; current-user ACLs; redaction before write | Startup chain verification; tamper detection; CI chain verification; mismatch alerts in redacted logs | Deny new sensitive operations on chain failure; preserve last verified chain head; Owner-reviewed recovery; no silent repair | Chain-of-custody tests; deletion/reorder/edit tamper tests; startup verification tests; WAL rollback tests |
| Unauthorized device access | Device paths, external drives, Windows shell/process launch, clipboard, USB/peripheral access | Prevent device access outside `L0`/`L1` or without `L2` approval | Default-deny device classification; `L3` hard-deny for forbidden local actions; destination validation; ACL/path isolation; no OmniRoute modification | AuditLedger device-access denials; policy-evaluation evidence; redacted path logging | Deny access; Owner preemption; no automatic retry | Device-path classification tests; `L2` approval tests; `L3` hard-deny tests; path traversal/normalization tests |
| Backup exposure | Google Drive backup selected by U-8R, local backup files, exported logs/config/audit data | Protect backup confidentiality and integrity without changing the confirmed storage choice | U-8R `Backup storage = Google Drive` preserved; proposed restricted private folder, explicit `G2`/`G4` approval, secret redaction, no raw secrets in backup, ₹0 quota, C-12 isolation, no personal filenames/private `Documents` listings | Backup content checks; audit of backup operations; redaction scans; retention/permission checks | Deny unsafe backup; quarantine exposed artifact after Owner review; rotate secrets if exposure confirmed | Backup redaction tests; no-secret config/log/audit tests; permission/retention tests; no paid-storage tests |
| Application crashes during sensitive operations | Approval state, SQLite WAL writes, hash-chain append, vault write, execution preflight | Avoid unauthorized starts or silent loss of audit/approval integrity; reconcile uncertain external outcomes | Transactional approval/audit writes; revalidation immediately before execution; fail-closed startup verification; idempotent execution boundary; last verified chain head | Crash-recovery tests; WAL integrity checks; duplicate/outcome reconciliation; redacted failure logs | Deny uncertain operation; recover last verified state; require new explicit Owner approval for unresolved in-flight action | Crash-injection tests for approval/audit/vault; WAL rollback tests; startup verification tests; duplicate/uncertain side-effect reconciliation tests |

## 3. Test principles

- Synthetic secrets only; no real credentials, tokens, or API keys in tests, logs, CI output, or fixtures.
- Windows-specific vault/ACL tests require a Windows runner or APEX.
- All tests are proposed for future M2 BUILD; none were implemented or run here.
- Every failure state must fail closed and produce a redacted audit record where storage is available.

## v1.1 additional proposed tests

Exact-operation binding tests must cover materially distinct inputs with identical redacted display and low-entropy secret protection; audit tests must cover full chain replacement, rollback and truncation against a separately protected checkpoint; preemption tests must cover revocation at each execution boundary and honestly reconcile already-started irreversible external effects. MFA factor/enrollment/recovery and device trust are unresolved designs, not provided by DPAPI alone. All tests remain future proposals.
