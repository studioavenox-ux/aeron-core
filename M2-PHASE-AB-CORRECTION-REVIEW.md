## Phase A correction and review

- `src/Aeron.Security/OwnerApprovalService.cs`: entries retain the verified requesting subject and kind; `Request` includes both in HMAC and `Consume` reauthenticates and checks both, entire request and exact binding. Owner-only decide/revoke/cancel, expiry, revalidation, audit failure latch and in-process single use remain. In-memory state is volatile and capped; a trusted clock can move backwards before expiry is observed. Callbacks execute under a reentrant lock; audit callbacks are guarded, but identity/grant callbacks need additional reentrancy hardening. External grant changes and side effects are not atomic with this lock. Consumption is never sufficient production authorization.
- `src/Aeron.Security/OperationBinding.cs`: V2 framed HMAC-SHA-256 binds identity kind as well as subject, action, ID, target, policy version and exact parameter bytes. Verification uses `CryptographicOperations.FixedTimeEquals`. The random instance key resides in managed process memory and is zeroed on disposal; other copies and OS/process compromise are outside its protection. Restart or disposal invalidates approvals. V1 and V2 bindings are deliberately incompatible and approvals are volatile.
- `src/Aeron.Security/OwnerAuthorityGuard.cs`: missing/throwing providers, empty evidence, invalid subjects and unrecognized identity kinds fail closed. Its guarantees depend on a genuinely trusted provider; it is not MFA, device trust or OS identity verification.
- `src/Aeron.Security/PolicyDecisionEngine.cs` and `src/Aeron.Contracts/SecurityPolicy.cs`: invalid/unknown actions or sensitivities and stale versions deny; explicit mappings and grants apply. Local path validation, remote gateway policy and secret access are unavailable and deny. G2/G3 and L0–L3 mappings are proposed engineering interpretations, not historical meanings. The action and sensitivity must be supplied by a trusted boundary.
- `src/Aeron.Contracts/ApprovalContracts.cs`: audit records contain only event kind and approval ID, no identity evidence, secret or operation contents. An audit sink is an interface, not a durable ledger.
- `src/Aeron.Core/FoundationHost.cs`: only the fail-closed policy with null provider and grants is exposed. No real identity, grant store, ledger, approval or production action dispatcher is wired.
- `tests/Aeron.Security.Tests/OperationBindingTests.cs` and `tests/Aeron.Security.Tests/OwnerApprovalServiceTests.cs`: added direct HMAC kind tampering and both Agent-to-Owner and Owner-to-Agent same-subject transitions, changed version plus kind, payload tampering, positive consumption, replay and concurrent consumes; existing different-subject and consume/revoke cases remain. These new changes are **not compiled or executed** here.

## Phase B — implemented foundations, not production integration

- `src/Aeron.Contracts/WindowsIdentityContracts.cs` and `src/Aeron.Security/WindowsOwnerIdentityProvider.cs` separate an OS-observed account from an independent trusted Owner verifier. Both are mandatory; a Windows login alone cannot establish Owner identity. Neither actual Windows SID source nor protected verifier/MFA/device implementation exists. No enrollment, factor or recovery choice is invented; host composition remains unchanged.
- `src/Aeron.Security/AuthorityState.cs` provides volatile explicit Owner-authenticated per-identity/action grants, no agent self-provisioning, session checks and Owner-authenticated session, agent and permission revocation. It denies without explicit grants; each check reauthenticates the session identity. Mutations are serialized in process, audited before granting, and revocations invalidate in memory even when audit fails; audit failure latches all authorization checks closed. A positive check is a snapshot, **not** dispatch authorization. It is not `IPermissionGrantStore`, not persistent, not wired into the host, and has no cross-process coordination, bounded capacity, protected provisioning UI, session expiry, principal lifecycle/reinstatement, policy-version scope or durable audit attribution. The fixed audit vocabulary and correlation IDs do not identify grant actor, target or action, so this is not yet an adequate production provisioning audit trail. Provider and sink trust, actual Owner MFA and protected access are prerequisites.
- `src/Aeron.Contracts/AuditLedgerContracts.cs` and `src/Aeron.Security/AuditLedger.cs` start a file-backed ordered SHA-256 chain with fixed-size records and no free-form credential-bearing data, contiguous sequences, exclusive file handle, full verification on append, flush-to-disk, and a separate externally protected checkpoint contract. Missing, mismatched or failed checkpoints latch unavailability; a crash between file flush and checkpoint update fails closed and needs controlled recovery. The file must already exist; no silent initialization. Callers must supply random correlation IDs, not encode sensitive material into them. There is **no production protected/rollback-resistant checkpoint provider, provisioning, recovery, ACL/hardening or backup/retention policy**, and rollback of both file and unprotected checkpoint cannot be detected. An external protected monotonic anchor is mandatory. Full-chain verification is O(n); file and checkpoint writes are not one atomic transaction. `FileShare.None` depends on cooperative/platform file-sharing semantics and does not defend a privileged process modifying the file outside those semantics. This is not connected to the approval audit interface, and it must not be claimed as a complete production ledger.
- New tests `tests/Aeron.Security.Tests/AuthorityStateTests.cs`, `AuditLedgerTests.cs`, and `WindowsOwnerIdentityProviderTests.cs` cover explicit grant/revocations/audit failure, chained append/tamper/truncation/checkpoint failure, and separation of account from Owner verification. They have not executed.

## Boundary for future side effects

A future trusted dispatcher must classify the actual operation and resolve the actual target and bytes, authenticate current identity/session, verify current protected policy and version, permissions, device trust and revocations, and validate the exact approval and durable audit. It must establish a concurrency protocol (e.g. one coordinated authority transaction/reservation with revocation ordered before irreversible dispatch), including crash recovery, before any external effect. Existing independent in-process locks and snapshot checks do not do this. Never authorize an action merely because an approval was consumed.
